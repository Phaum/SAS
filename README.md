# Перенос 3x-ui и nginx через SSH

## Рекомендуемый сценарий: запуск на новом сервере

Для автономной миграции 3x-UI, nginx, подписок и панели логирования выполните на **новом** Debian/Ubuntu сервере:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Phaum/SAS/main/bootstrap-migrate.sh)
```

Сценарий запросит доступ к старому серверу и REG.RU, проверит SSH fingerprint, перенесёт согласованный snapshot базы, подготовит новый сервер, покажет dry-run DNS, переключит A-записи только после подтверждения и завершит установку. При ошибке после DNS-переключения он попытается вернуть записи на старый IP.

Подробности и ограничения: [README-bootstrap.md](README-bootstrap.md). Старый сценарий ниже оставлен для ручного переноса с третьей управляющей машины.

Один Bash-скрипт, без Python. **По умолчанию автоматически устанавливает зависимости и выполняет перенос.** Запускается с Linux-машины, имеющей SSH-доступ к обоим серверам. Обязательные аргументы — IPv4 источника и цели. Через машину запуска проходит архив с секретами; временные каталоги создаются с закрытыми правами.

## Требования

- Обычная установка 3x-ui, systemd, стандартная SQLite `/etc/x-ui/x-ui.db`. Docker и PostgreSQL не поддерживаются.
- Одинаковые дистрибутив, версия Debian/Ubuntu и архитектура процессора. UID/GID `www-data` должны совпадать; владельцев с другими UID/GID нужно проверить самостоятельно.
- На обеих машинах: Debian/Ubuntu с Bash 4+, systemd, APT, стандартными базовыми утилитами и SSH-сервером. На источнике уже работает 3x-ui и nginx, установленный через APT. На машине запуска: Bash, SSH-клиент, scp, coreutils.
- SSH root по паролю. На обоих серверах должен быть разрешён такой вход; скрипт не меняет настройки sshd. Для передачи пароля используется sshpass, при отсутствии он автоматически устанавливается локально через APT с root или `sudo -n`.
- APT-репозитории цели должны предоставлять пакеты nginx, модулей и Certbot, используемые источником. Скрипт определяет установленные пакеты `nginx*`, `libnginx-mod-*`, `certbot`, `python3-certbot*` и автоматически устанавливает их вместе с базовыми утилитами. Самописные сборки nginx и перенос сторонних APT-репозиториев не поддерживаются. Пакеты устанавливаются доступных в репозиториях версий, без принудительного совпадения с версией источника.
- Достаточное место на машине запуска, на источнике для архива, на цели для архива, распакованных данных и резервной копии. Проверка `3 × размер сжатого архива` — только предварительная оценка для `/var/tmp`, а не гарантия места на всех файловых системах.

## Запуск

Сначала подключитесь к каждому серверу обычным `ssh root@IP` и проверьте отпечаток ключа сервера по доверенному каналу. Скрипт использует `StrictHostKeyChecking=yes`: неизвестные или изменившиеся ключи не принимаются автоматически.

Проверки без переноса:

```bash
bash migrate-3xui.sh 192.0.2.10 198.51.100.20 --check
```

Полностью автоматическая установка и перенос с заменой перечисленных ниже каталогов цели:

```bash
bash migrate-3xui.sh 192.0.2.10 198.51.100.20
```

С отдельными SSH-портами:

```bash
bash migrate-3xui.sh 192.0.2.10 198.51.100.20 \
  --source-port 2222 --target-port 22
```

При отдельном запуске пароли источника и цели запрашиваются скрыто. Для автоматизации передайте `SOURCE_SSH_PASSWORD` и `TARGET_SSH_PASSWORD` через окружение; управляющий скрипт делает это из `.env`. Ключи не используются. Пароли передаются sshpass через файловый дескриптор, не аргументы команд.

Адреса в примерах демонстрационные. На цели будут заменены **целиком** следующие пути, включая удаление существующего пути, если его нет на источнике:

```text
/etc/x-ui
/usr/local/x-ui
/usr/bin/x-ui
/etc/systemd/system/x-ui.service
/etc/systemd/system/x-ui.service.d
/etc/default/x-ui
/etc/nginx
/etc/letsencrypt
/root/cert
/var/www
```

`--check` проверяет доступ, совпадение ОС/архитектуры, исходную установку и получает список пакетов. Он не устанавливает пакеты и не выполняет полную проверку ещё не подготовленной цели. В автоматическом режиме после установки дополнительно проверяются nginx, UID/GID и состояния служб цели.

Бинарные файлы 3x-ui и Xray копируются с источника, поэтому версия сохраняется; отдельно скачивать и устанавливать панель не требуется. Перед упаковкой исходный x-ui останавливается, после упаковки запускается обратно. Длительность остановки зависит от размера всех переносимых файлов. nginx источника продолжает работать. На время копирования не меняйте панель, сертификаты и файлы сайта; динамические базы сайтов этот скрипт не переносит.

На цели скрипт устанавливает пакеты без интерактивных вопросов, затем останавливает службы, создаёт резервную копию прежних файлов, распаковывает переносимые данные, выполняет `nginx -t`, включает автозапуск и запускает службы. Через пять секунд проверяет, что обе службы активны. При ошибке после создания backup пытается восстановить прежние файлы и состояния служб. **Откат файлов возвращает состояние после установки пакетов; APT-изменения не откатываются.** Если установка пакетов завершится ошибкой, перенос данных не начнётся.

## Откат

Перед применением скрипт печатает команду для выполнения **на целевом сервере**:

```bash
bash /var/tmp/3xui-target-XXXXXXXX/migrate-3xui.sh \
  --worker rollback /var/tmp/3xui-target-XXXXXXXX
```

Используйте фактический путь из вывода. Откат доступен после появления файла `READY` — он означает, что резервная копия завершена. Откат заменит переносимые каталоги прежними данными, включая изменения, сделанные после миграции.

Резервная копия и полученный архив остаются на цели с закрытыми правами. После проверки перенесите backup в постоянное защищённое хранилище: `/var/tmp` может очищаться системой. Архив содержит базу пользователей, ключи и сертификаты.

При потере питания, `kill -9` или обрыве SSH автоматическое восстановление не гарантируется. Проверьте `systemctl status x-ui nginx` на обеих машинах; при необходимости запустите исходный x-ui и выполните ручной откат цели. Одновременные миграции и редактирование переносимых данных не поддерживаются.

## Что проверить перед переключением

- Скрипт сохраняет IP и домены внутри конфигов и базы без изменений. Проверьте `listen`, привязки inbound и адреса подписок. Конфигурация с привязкой к старому IP может не запуститься на цели; в этом случае проверка nginx/служб приведёт к откату. Универсальная замена IP в SQLite и текстах намеренно не выполняется.
- Нестандартные каталоги сертификатов, внешние nginx `include`, файлы вне `/var/www`, зависимости кастомного unit x-ui и другие внешние пути не входят в перенос. Проверьте их до запуска.
- `/root/.acme.sh`, cron, пользовательские службы/таймеры certbot, firewall, sysctl, маршруты, DNS, SSH-конфигурация и прочие настройки ОС не переносятся. Certbot и его DNS-плагины, установленные через APT на источнике, устанавливаются автоматически; стандартный таймер предоставляется пакетом. Проверьте продление и внешние файлы DNS-credentials; Snap, pip и acme.sh требуют отдельной поддержки. Не запускайте конкурентное продление на двух серверах после переключения.
- Откройте необходимые порты в firewall и панели провайдера. Проверьте панель, HTTPS с правильным доменом/SNI, подписки и реальные клиентские подключения. Активность systemd не является проверкой доступности из интернета.
- После проверки переключите DNS или IP клиентов. Источник остаётся запущенным: после создания архива базы двух серверов расходятся, последующие изменения и статистика автоматически не синхронизируются.

Скрипт рассчитан на стандартный перенос на Debian/Ubuntu с рабочим SSH и APT. Проверены синтаксис, аргументы и обработка ошибок на имитациях команд; на реальных серверах в этой сессии он не запускался.

Документация: [резервное копирование 3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/operations/backup-restore.mdx), [проверка конфигурации nginx](https://nginx.org/en/docs/switches.html).
