# Управление переносом

Положите рядом три файла:

```text
manage-migration.sh
migrate-3xui.sh
regru-change-ip.sh
```

Запустите на Linux-машине с SSH-доступом к обоим серверам:

```bash
bash manage-migration.sh
```

При первом запуске скрипт запросит IPv4 серверов, SSH-порты и отдельные пароли root для источника и цели, DNS-зону и при необходимости имя записи, старый/новый IPv4 в DNS, логин и пароль API REG.RU. Все пароли вводятся скрыто. SSH выполняется от root по паролю через `sshpass`; ключи не используются. На обоих серверах должен быть уже разрешён парольный вход root. Скрипт не изменяет настройки SSH-сервера.

Настройки сохраняются в `.env` рядом со скриптами с правами `600`. При следующих запусках заполненные настройки используются автоматически; отсутствующие обязательные данные запрашиваются. Для изменения существующих настроек запустите `--configure` или отредактируйте `.env`. Enter сохраняет текущее значение; чтобы очистить опциональное поле, оставьте его пустым в `.env` вручную.

## Последовательность

1. Проверка доступа к REG.RU и плана DNS без записи — чтобы выявить ошибки API до остановки исходной панели.
2. Автоматическая установка зависимостей на цели и миграция 3x-ui/nginx.
3. Дополнительная проверка `nginx -t` и активности x-ui/nginx на цели через SSH.
4. Замена совпадающих A-записей через REG.RU.

При ошибке миграции DNS не меняется. После успешной миграции состояние сохраняется как `dns-pending`: при ошибке DNS повторите ту же команду, и скрипт продолжит только DNS, не копируя старую базу поверх новой. Если целевые службы перестали работать, смена DNS блокируется до исправления.

Эти проверки подтверждают состояние служб, а не работу клиентского трафика. До запуска должны быть готовы порты/firewall, нужные IP-привязки, сертификаты на цели. DNS переключается автоматически без отдельного запроса подтверждения. Все ограничения двух отдельных скриптов сохраняются: [миграция](README.md), [REG.RU](README-regru.md).

## Файл .env

Пример находится в `.env.example`. Можно скопировать его в `.env` и заполнить вручную:

```bash
cp .env.example .env
chmod 600 .env
```

Формат **буквальный `KEY=value`**, одна настройка на строку. Не добавляйте внешние кавычки: кавычки, пробелы, `#`, `$`, обратные слеши и `=` после первого знака `=` считаются частью значения. Строки, начинающиеся с `#`, — комментарии. Подстановка переменных и shell-команды не выполняются. Не используйте `source .env`: файл предназначен для встроенного безопасного чтения управляющим скриптом. Многострочные значения не поддерживаются.

Секреты лежат в открытом виде на диске; права `600` ограничивают доступ, но не шифруют их. `.gitignore` исключает `.env`, состояние и DNS-backup из Git. Пароль API передаётся через окружение только DNS-подпроцессу. Пароли SSH передаются только процессу миграции, который снимает с переменных признак экспорта и передаёт нужный пароль `sshpass` через файловый дескриптор. Пароли не включаются в аргументы команд или файлы состояния. Дочерний DNS-скрипт временно хранит запрос в закрытом каталоге и удаляет его при штатном завершении.

Пароли SSH хранятся в `.env` как `SOURCE_SSH_PASSWORD` и `TARGET_SSH_PASSWORD`. Если `.env` создан старой версией, устаревшее поле `SSH_IDENTITY` игнорируется и удаляется при сохранении, а отсутствующие пароли запрашиваются. Смена способа входа и паролей не сбрасывает прогресс миграции.

## Полезные команды

Только собрать и сохранить настройки:

```bash
bash manage-migration.sh --configure-only
```

Проверить доступ и конфигурацию:

```bash
bash manage-migration.sh --check
```

Без вопросов с подготовленным `.env`:

```bash
bash manage-migration.sh --non-interactive
```

Отдельный файл настроек:

```bash
bash manage-migration.sh --env /opt/migration/.env --non-interactive
```

Родительский каталог `.env` должен существовать. В нём создаются `.migration-state` и `regru-backups`. По умолчанию используется `.env` рядом с управляющим скриптом, независимо от текущего рабочего каталога.

`--check` может сохранить введённые настройки и установить локальные curl/jq/sshpass, но не переносит данные и не изменяет DNS. Требуются Bash 4.3+, SSH-клиент, GNU coreutils и `flock` из util-linux. `sshpass` устанавливается автоматически через APT с root или `sudo -n`; на других дистрибутивах установите его заранее. Неизвестные SSH host keys не принимаются автоматически: заранее проверьте отпечатки при обычном SSH-подключении. Для REG.RU заранее разрешите IP машины запуска в настройках API.

## Прерванный запуск

В `.migration-state` хранится этап для комбинации серверов, домена и IP-настроек. После успешного завершения повторный запуск с той же конфигурацией ничего не переносит. Изменение паролей SSH/API, логина API или портов не сбрасывает прогресс. Изменение серверов или DNS-настроек создаёт другой запуск — не меняйте их при продолжении частично выполненного переноса.

Если сохранено `migration-started`, предыдущая миграция завершилась ошибкой или процесс оборвался. Автоматически повторять копирование небезопасно для новых данных, поэтому скрипт останавливается и печатает путь состояния. Проверьте оба сервера и резервную копию:

- Если перенос завершён и новый сервер исправен, запишите `dns-pending` в **тот конкретный файл состояния**, путь которого был выведен.
- Если перенос не состоялся, цель восстановлена и повторный перенос допустим, запишите `new` в этот файл.

Например, после проверки:

```bash
printf '%s\n' dns-pending > /путь/.migration-state/ФАКТИЧЕСКИЙ_ХЭШ.state
bash manage-migration.sh
```

Для сознательного повторного переноса уже завершённой конфигурации также потребуется заменить `done` на `new` в соответствующем файле. Это снова заменит целевые данные копией с источника.

На реальных серверах и аккаунте REG.RU управляющий сценарий не запускался. Проверены порядок вызовов, остановка при ошибках, продолжение DNS, повторный запуск после успеха и буквальная обработка секретов на имитациях дочерних команд.

Поддерживается только IPv4. Старые настройки IPv6 из `.env` игнорируются и удаляются при сохранении; ранее сохранённый прогресс подхватывается. Существующие AAAA-записи не изменяются.
